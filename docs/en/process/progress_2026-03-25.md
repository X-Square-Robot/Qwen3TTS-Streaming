# Qwen3-TTS Triton 项目阶段进展（2026-03-25）

## 1. 项目目标

当前项目的目标不是单纯把模型跑起来，而是形成一条可自动部署、可验证、可扩展的生产链路：

1. `autorun` 能根据用户设备部署当前最优实现。
2. `talker + code predictor + code2wav` 融合为单图，支持纯流式推理。
3. Triton BLS 能正确处理长文本，在接近 decode 上限时自然分段并重启 session。
4. 主链路最终支持高性能多路拼 batch。
5. 对线上场景中相对稳定的 instruct / prefix，支持 prefix KV cache，从而让主链路长期停留在高效 batched decode。

当前工作已经从“导出与部署原型”推进到“工程化验证与精度/编译问题排查”阶段。

---

## 2. 当前总体结论

截至目前，可以明确得到以下结论：

1. **BLS 不是当前随机噪声音频的主因。**
   已通过 direct backend 对比证明，`talker_code2wav_fused` 的 Triton TensorRT backend 在绕过 orchestrator/BLS 的情况下就已经与 ORT 产生数值分叉。

2. **当前线上阶段 repo 的 fused TRT 确实是 `FP16`。**
   该配置在当前 fused 图上数值不稳定，`step0` 就会严重发散，因此不能作为生产默认精度。

3. **`BF16` 明显优于 `FP16`，但仍不能保证 fused TRT 与 ORT 的逐步一致。**
   `BF16` 下 `step0` 已可对齐，但在后续 decode 中仍会出现分叉。

4. **即使使用 `FP32` TRT，fused 图也不是完全逐步等价于 ORT。**
   `FP32` 下 `step0` 几乎完全对齐，主 token 可维持更久，但 `code predictor` 的后续 code group 仍会先发生分叉，主 token 最终在后续 step 漂移。

5. **因此当前问题不是单一问题。**
   现状是两个问题叠加：
   - `FP16` 精度不足，直接不可用。
   - fused TRT 图中的 `code predictor unroll / argmax` 路径，即使在更高精度下也存在小的语义偏差。

## 4. 已验证结果

### 4.1 官方原型 / 输入格式基线

已修正官方 API 的输入格式与调用方式，官方原型音频基线已确认可正常生成完整音频，不再是只输出“你好”或错误长度的异常状态。

这一步的意义是：

1. 官方原型可作为当前所有后续验证的听感基线。
2. 之后所有 ONNX / TRT / Triton 的比对都应与这个基线链路对齐。

### 4.2 `FP16` fused TRT backend 结论

当前阶段 Triton repo 使用的是 `FP16` fused engine。

direct backend 验证结果表明：

1. `step0 prefill` 就已经出现严重分叉。
2. `wav_cos` 接近 0，生成结果会退化为随机噪声级别。

结论：

- `FP16` 在当前 fused 图上不可接受。
- 当前生产主线不应继续以 `FP16` 作为默认推理精度。

### 4.3 `BF16` fused TRT backend 结论

手工构建 BF16 fused engine 后，direct backend 验证结果表明：

1. `step0` 已可与 ORT 对齐。
2. `step1` 主 token 仍可一致。
3. 但 `code predictor` 的后续 token 已开始分叉。
4. `step2` 起主链路开始明显漂移。

同时，逐 stage CP 诊断显示：

1. 有些 stage 确实属于接近并列时的 argmax 摇摆。
2. 但也存在 gap 明显不小却选出完全不同 token 的情况。

结论：

- `BF16` 比 `FP16` 好很多，是更合理的候选精度。
- 但 `BF16` 仍不足以证明 fused TRT 已达到与 ORT 语义等价。

### 4.4 `FP32` fused TRT backend 结论

已手工编译 `FP32` fused TRT engine，并单独组装 direct Triton repo 做验证。

结果：

1. `step0` 几乎完全对齐 ORT。
   - `hidden_cos`、`logits_cos`、`codec_sum_cos` 约等于 1
   - `wav_cos = 0.999545`

2. `step1`、`step2` 主 token 仍可保持一致。

3. 但 `code predictor` 的后续 code group 已在更早阶段开始分叉。

4. 扩展到更多 step 后，主 token 会在后续 step 漂移。

结论：

- `code2wav` 在 `FP32` 下不是当前首要问题。
- 更核心的问题已经收缩到 `fused TRT` 中的 `code predictor unroll / argmax / codec_sum` 路径。

### 4.5 BLS 责任边界结论

当前已经可以明确：

1. **随机噪声问题不是 BLS 脚本本身导致的。**
2. 当前最主要的问题在 engine/backend 层，而不是 orchestrator 的输入拼装。

这意味着当前排障优先级应当是：

1. 先把 fused TRT backend 的数值/语义问题钉死。
2. 再继续推进 BLS 侧 continuous batching、prefix cache 调度与长文本编排。

## 6. 当前主要问题清单

### 问题 1：`FP16` fused TRT 不可用

表现：

1. `step0` 即严重发散
2. `wav` 直接失真
3. 输出呈随机噪声

结论：

- 这不是可通过 BLS 修补的问题。

### 问题 2：`BF16` 仍会在 decode 过程中发生 CP 语义分叉

表现：

1. `step0` 对齐
2. `step1` 主 token 一致，但部分 CP group 已漂
3. 后续 `codec_sum` 被带偏，导致主链路进一步发散

### 问题 3：即使 `FP32`，fused TRT 仍非严格等价于 ORT

表现：

1. `step0` 几乎完美
2. 但 CP 后续 group 仍出现差异
3. 主 token 延后发散

这说明当前剩余问题更偏向：

1. TensorRT 对 fused 图中特定子路径的 lowering 语义差异
2. 或者当前 fused 图结构过于敏感，不适合把 CP unroll 与 argmax 全部压在同一 TRT 子图内

### 问题 4：当前 build 脚本的 fused precision 选择存在认知陷阱

已发现：

1. fused build 路径的实际精度与 I/O format 主要由 `triton_manifest.json` 驱动。
2. 单纯传 `ENGINE_DTYPE=bf16` 并不会可靠覆盖 fused build 配置。

这会导致用户误以为自己在编 `BF16`，但实际 repo/engine 仍是 `FP16`。

## 8. 当前推荐主线

从当前证据看，推荐主线如下：

1. **停止以 `FP16 fused TRT` 为目标继续推进。**
2. **把 `BF16` 视为更合理的默认候选，但不直接宣布其已可上线。**
3. **优先拆解 `code_predictor_unrolled` 的 TRT 语义偏差。**
4. **在 engine/backend 彻底稳定前，不继续扩大 orchestrator/scheduler 的复杂度。**
5. **长文本分段、prefix cache、scheduler 相关代码继续保留，但视为“待 engine 稳定后再做收益化”的第二层工作。**
