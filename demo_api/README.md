# demo_api

WebUI demo API service for Qwen3TTS-Streaming.

## Overview

demo_api provides the backend endpoints for the three core demo panels of the frontend WebUI:

| Panel | Description |
|------|------|
| **Text Player** | Real-time streaming TTS playback; WebSocket pushes audio and events token by token |
| **LLM PK** | Streaming vs. offline side-by-side comparison, quantifying the difference in first-packet latency and total time |
| **Concurrency** | Concurrency stress test, supporting real Triton requests or simulated mode, with real-time progress reporting |

## Dependencies

```
pip install -r requirements.txt
```

Core dependencies:

- `qwen3-tts-client[all]` — TTS client and Triton gRPC communication
- `aiohttp>=3.9` — HTTP/WebSocket serving framework
- `numpy>=1.24` — audio data processing

## Quick Start

**Option 1: Run directly**

```bash
python -m demo_api
# Listens on 0.0.0.0:7860 by default
```

Optional arguments: `--host`, `--port`.

**Option 2: One-click launch (recommended)**

```bash
bash scripts/demo/start_webui_demo.sh
```

This script automatically brings up Triton, demo_api, and the Vite WebUI — ready to use out of the box.
It supports options such as `--variant`, `--triton-slots`, `--no-triton`, and `--simulated-concurrency`.

## Environment Variables

| Variable | Default | Description |
|------|--------|------|
| `QWEN_DEMO_TRITON_GRPC` | `localhost:8001` | Triton gRPC address |
| `QWEN_DEMO_TRITON_MODEL` | `tts_orchestrator` | Triton model name |
| `QWEN_DEMO_DEFAULT_SPEAKER` | `Serena` | Default speaker |
| `QWEN_DEMO_DEFAULT_LANGUAGE` | `auto` | Default language |
| `QWEN_DEMO_DEFAULT_MS_PER_TOKEN` | `30` | Simulated upstream token rate for LLM PK (ms/token) |
| `QWEN_DEMO_HOST` | `0.0.0.0` | API listen address |
| `QWEN_DEMO_PORT` | `7860` | API listen port |
| `QWEN_DEMO_CORS_ORIGIN` | `*` | Allowed CORS origin |
| `QWEN_DEMO_ENABLE_LIVE_CONCURRENCY` | `1` | Whether to enable real concurrent requests (`0` for simulated mode) |
| `TRITON_MAX_BATCH_SLOTS` | `128` | Maximum Triton batch slots |
| `TRITON_MAX_SESSIONS` | `128` | Maximum Triton sessions |

## API Endpoints

### HTTP

| Method | Path | Description |
|------|------|------|
| GET | `/healthz` | Health check, returns `{"ok": true}` |
| GET | `/api/v1/capabilities` | Get backend capabilities, default parameters, runtime configuration, and declared limits |
| POST | `/api/v1/llm-pk` | Run the LLM PK comparison (streaming + offline), returns both results |
| POST | `/api/v1/concurrency` | Create a concurrency stress-test job, returns a `job_id` |
| GET | `/api/v1/audio/{audio_id}` | Fetch audio files generated by scenarios such as LLM PK |

### WebSocket

| Path | Description |
|------|------|
| `/api/v1/trt-live` | Text Player real-time streaming TTS; send `{"type":"speak",...}` to start |
| `/api/v1/concurrency/{job_id}` | Concurrency stress-test progress push, until a `summary` message is received |

## Relationship to the client Package

demo_api depends on `schemas` (e.g. `TraceEvent`) and `triton_types` (e.g. `TtsRequest`) from the `qwen3tts_protocol` package
for the structured definitions of requests/responses. The actual Triton gRPC communication is wrapped by the `triton_client` module,
so demo_api no longer embeds client logic and keeps a single responsibility.
